# Данные: лидарные записи из тоннелей метро

Контекст для задачи **обнаружения препятствий беспилотным поездом и оценки расстояния до них**.
Ниже — то, что уже установлено по фактическому содержимому файлов. Раздел «Гипотезы» отделён
намеренно: там выводы по косвенным признакам, их стоит перепроверить.

---

## 1. Что это за данные

Шесть записей **rosbag2** (формат v5, хранилище sqlite3), суммарно 22 ГиБ, 2488 кадров.
Каждая папка — отдельная запись, внутри один `.db3` и `metadata.yaml`.

В каждой записи **ровно один топик**, но **имя у него разное**:

| Запись | Топик |
|---|---|
| `doubleT_obstacle` | `/sensing/lidar/hesai128/pointcloud` |
| остальные пять | `/lidar_points` |

Тип везде `sensor_msgs/msg/PointCloud2`, сериализация `cdr`. Это наблюдение по шести
имеющимся записям, а не гарантия: на контрольном баге имя может быть третьим, поэтому
соединение надо выбирать **по типу сообщения**, а не по имени топика.

Больше ничего нет. **Нет камер, нет одометрии, нет IMU, нет TF, нет разметки/аннотаций,
нет калибровок.** Только сырая геометрия с одного лидара. Это ключевое ограничение задачи:
любой метод должен работать по одному облаку точек (или по их последовательности).

| Папка | Кадров | Точек/кадр | Длит. | Частота | Размер |
|---|---:|---:|---:|---:|---:|
| `doubleT_obstacle` | 201 | 921 600 | 20.4 с | 9.9 Гц | 4.5 ГиБ |
| `doubleT_platform` | 345 | 307 200 | 34.4 с | 10.0 Гц | 2.6 ГиБ |
| `roundT_doubleT` | 252 | 307 200 | 25.1 с | 10.1 Гц | 1.9 ГиБ |
| `roundT_pressureGate_roundT` | 268 | 307 200 | 26.7 с | 10.0 Гц | 2.0 ГиБ |
| `roundT_squareT_pressureGate_squareT` | 545 | 307 200 | 55.4 с | 9.8 Гц | 4.1 ГиБ |
| `squareT_platform_squareT_switch` | 877 | 307 200 | 88.2 с | 9.9 Гц | 6.6 ГиБ |

**Внимание:** `doubleT_obstacle` отличается от остальных пяти не только содержимым —
она писалась другой установкой лидара, см. §4.4.

## 2. Структура одного кадра

```
запись (папка)
  └── кадр = одно сообщение PointCloud2, ~10 раз в секунду
        └── точка (307 200 или 921 600 штук)
              └── 6 полей
```

Параметры сообщения (замерено на `doubleT_obstacle`, кадр 0):

```
height = 1, width = 921600      # облако помечено как НЕорганизованное
point_step = 26, row_step = 23961600
is_bigendian = False, is_dense = False
frame_id = "lidar_livox"
```

Раскладка точки — **упакованная, без выравнивания**:

| поле | тип | смещение | смысл |
|---|---|---:|---|
| `x` | float32 | 0 | метры |
| `y` | float32 | 4 | метры |
| `z` | float32 | 8 | метры |
| `intensity` | float32 | 12 | 0…255 |
| `ring` | uint16 | 16 | номер луча, 0…127 |
| `timestamp` | float64 | **18** | часы сенсора, см. §3 |

`timestamp` лежит по смещению 18, не кратному 8. numpy-dtype строить **только** через явные
`offsets` + `itemsize`, `aligned=True` использовать нельзя:

```python
DT = np.dtype({
    "names":   ["x", "y", "z", "intensity", "ring", "timestamp"],
    "formats": ["<f4", "<f4", "<f4", "<f4", "<u2", "<f8"],
    "offsets": [0, 4, 8, 12, 16, 18],
    "itemsize": 26,
})
a = np.frombuffer(msg.data, dtype=DT, count=msg.width * msg.height)
```

## 3. Подводные камни (все проверены на данных)

**3.1. «Нет возврата» записан нулями, а не NaN.**
`is_dense=False`, но `np.isnan` не находит ничего: пустые лучи записаны как `(0, 0, 0)`.
В кадре 0 записи `doubleT_obstacle` из 921 600 ячеек реальных измерений **346 808, то есть 38 %**;
остальные 62 % — пустые. Фильтровать нужно по норме:

```python
keep = np.linalg.norm(xyz, axis=1) > 1e-6
```

Массив всегда имеет фиксированный размер 128 лучей × N угловых шагов независимо от содержимого.

**3.2. Двойной возврат (dual return).**
На каждый выстрел луча приходится ровно 2 точки: в `doubleT_obstacle` 3600 уникальных меток
времени × 2 = 7200 точек на кольцо; в остальных 1200 × 2 = 2400. Скорее всего это пара
«сильнейшее эхо / последнее эхо». **Половина точек — дубли по направлению**, отличающиеся
дальностью. Пара определяется совпадением `(ring, timestamp)`. Для большинства задач их надо
схлопывать, это вдвое сокращает объём.

**3.3. Часы лидара не синхронизированы с системными.**
Поле `timestamp` точек ≈ 946 687 297 с — это эпоха 2000-01-01 плюс ~42 минуты, собственное время
сенсора без PTP/GNSS. А `header.stamp` = 1 788 354 623 110 040 384 нс — реальное время записи
(2026-09-02). **Складывать или сравнивать их напрямую нельзя.** Для компенсации движения внутри
кадра (deskew) использовать только относительное время: `t - t.min()`.

**3.4. Разная скорость вращения у разных записей.**
Темп выстрелов везде одинаковый — 36 000 угловых шагов в секунду. Различается период оборота:

| | оборот | шаг по азимуту | покрытие времени кадром |
|---|---|---|---|
| `doubleT_obstacle` | 100 мс (10 Гц) | 0.1° | сплошное |
| остальные пять | 33 мс (30 Гц) | 0.3° | треть, между кадрами слепые 67 мс |

То есть в пяти записях лидар крутится втрое быстрее, каждый кадр — полный оборот, но пишется
только каждый третий. Геометрия полная, но **между соседними кадрами разрыв 67 мс**: объект
на скорости 60 км/ч за это время смещается на 1.1 м. Для оценки скорости сближения это важно.

**3.5. `frame_id` не совпадает с именем топика.**
Топик называется `hesai128`, а `header.frame_id` = `lidar_livox`. Откуда расхождение — неизвестно.
TF-дерева в записях нет, так что положение сенсора относительно поезда/рельсов **не задано**.

**3.6. Ось движения — минус Y, а не плюс X.**
Габариты кадра 0 (`doubleT_obstacle`), после фильтрации пустых:

```
x: -8.67 … +7.07 м      (поперёк)
y: -208.67 … +3.53 м    (вдоль, обзор вперёд ~209 м)
z: -7.03 … +2.83 м      (вертикаль)
дальность: 0 … 208.8 м
```

Сцена вытянута вдоль **−Y**. Это нарушает конвенцию REP-103 (x вперёд), так что все формулы,
взятые из типовых ROS-примеров, надо править под эту ось либо один раз повернуть облако.

**3.7. Лучи по углу места расположены НЕравномерно, и ближняя зона от этого страдает.**
Замер на `roundT_doubleT`, кадр 30 (лидар 1.33 м над путевым основанием): для каждого
из 128 колец взят медианный угол места, затем посчитано, сколько колец попадает в окно,
которое занимает предмет высотой 0.30 м, стоящий на УГР:

| дальность | окно углов | лучей в окне |
|---|---|---:|
| 6 м | −9.66°…−7.56° | **4** |
| 8 м | −7.27°…−5.68° | 7 |
| 10 м | −5.83°…−4.55° | **10** |
| 15 м | −3.89°…−3.04° | 7 |
| 20 м | −2.92°…−2.28° | 6 |
| 25 м | −2.34°…−1.82° | 4 |

Ниже примерно −6° шаг по углу места растёт. Число точек на низком предмете — это
«лучи в окне × азимутальные отсчёты»: второй множитель растёт как 1/d, первый ниже
10 м падает, и произведение имеет **максимум около 10–15 м**.

Следствие, неочевидное и проверенное инъекцией: у предмета высотой 0.25–0.30 м точек
на 6 м **меньше**, чем на 12 м (62–72 против 139), и доля обнаружения в полосе 5–10 м
проседает вдвое. Любая модель вида «точек ≈ k·A/d²» в ближней зоне завышает, и порог
`min_points`, построенный по ней, там строже, чем задумано.

Величина привязана к установке: у `doubleT_obstacle` лидар на 1.71 м и втрое выше
угловое разрешение, поэтому окна и число лучей там надо пересчитывать, а не переносить.

**3.8. Сечение пути несимметрично: «середина пола» — не ось пути.**
Замер 2026-09-22 (`tools/measure_cross_check.py`, профиль точек у уровня основания):
контактный рельс на `roundT_doubleT` и `squareT_platform_squareT_switch` стоит
**слева** (1.35–1.60 м от середины колеи, 0.25–0.70 м над основанием) и затеняет
пол за собой, а справа пол открыт до стены (до 1.95 м и до 2.30 м соответственно).
Поэтому центр полосы основания уезжает **вправо** от середины колеи на всех пяти
записях, где полосу видно: медиана −45…−135 мм, и смещение растёт с дальностью
(−20…−50 мм на 5–10 м, −90…−170 мм на 22–27 м). Любая оценка оси «по краям пола»
несёт это смещение. Середина колеи по гребням головок рельсов смещения не имеет;
колея по гребням — 1498–1540 мм (p10–p90 по записям).

На двухпутных участках полоса основания шире нормы и как опора не работает вовсе;
соседний путь на `roundT_doubleT` появляется с кадра ≈ 94, слева.

## 4. Гипотезы (не подтверждены, требуют проверки)

**4.1. Это метро, `T` = tunnel.** Названия папок расшифровываются как последовательность
проезжаемых участков:

| папка | предположительно |
|---|---|
| `roundT_doubleT` | круглый тоннель → двухпутный |
| `roundT_pressureGate_roundT` | круглый → гермозатвор → круглый |
| `roundT_squareT_pressureGate_squareT` | круглый → прямоугольный → гермозатвор → прямоугольный |
| `squareT_platform_squareT_switch` | прямоугольный → станция → прямоугольный → стрелка |
| `doubleT_platform` | двухпутный тоннель → станция |
| `doubleT_obstacle` | двухпутный тоннель → **препятствие** |

Гермозатвор, платформа, стрелочный перевод — набор объектов метрополитена. Косвенно
подтверждается геометрией: длинный узкий коридор (209 м вперёд при поперечнике ~15 × 10 м).

**4.5. Содержимое `doubleT_obstacle` — ПРОВЕРЕНО оракулом разметки.**
Запись двухпутная (междупутье 4.17 м, колея 1.522 м). В кадре два человека
в световозвращающих жилетах:

- **дальняя фигура** на 54.7–56.7 м, видна все 200 кадров. Пересекает путь:
  в кадрах ~19–69 находится **в габарите своего пути** (в части кадров строго
  по оси), затем уходит в междупутье и с кадра ~140 стоит неподвижно;
- **ближняя фигура** появляется на кадре 165 и убегает от лидара с 5.3 м
  до 16.1 м к кадру 200, скорость 3.1 м/с. Всё это время идёт **по междупутью**,
  в габарит своего пути не попадает ни в одном кадре.

Ось пути развёрнута к оси лидара на 1.61°, поэтому «на каком пути стоит объект»
нельзя определять по одной координате `y`: на 55 м ось пути смещена на −1.44 м.

**Жилеты использовать для детекции нельзя.** Отклик 255 при медиане по кадру 11
находит фигуры тривиально, но детектор выучит жилет, а не препятствие. В конфиге
стоит `detector.use_intensity: false`, и включение завершается ошибкой загрузки.
Интенсивность применяет только офлайновый оракул разметки `tools/oracle.py`.
**Исключение, найденное 2026-09-22:** одометрия ядра (`core/odometry.py`,
`odometry.channels`) строит продольный профиль и по каналу интенсивности —
жилет в кадре становится её ориентиром. Планируется убрать, пока не сделано.

**4.2. `doubleT_obstacle` — целевой сценарий.** Единственная запись, названная по событию,
а не по типу участка; единственная с втрое большим разрешением. Похоже, это и есть кейс
с препятствием, а остальные пять дают «нормальную» обстановку для сравнения и для обучения
модели фона.

**4.4. `doubleT_obstacle` писалась другой установкой, чем остальные пять.**
Замер плоскости основания по кадрам (полный RANSAC, 30–126 кадров на запись) даёт
высоту лидара над путевым основанием **1.71 м** у `doubleT_obstacle` и **1.31 м**
у всех остальных, при базовом крене **+3.9°** против примерно **−0.5°**. Жёстко
закреплённый на одном составе сенсор такого дать не может. Это согласуется с тем,
что у неё другое имя топика, втрое выше разрешение и втрое ниже частота вращения.

Следствие: параметры, привязанные к высоте лидара или к уровню крена, между записями
не переносятся. Подтвердить независимо можно замером ширины колеи (должна выйти
1520 мм в обеих) — величина от установки не зависит.

**4.3. Поезд движется — ПРОВЕРЕНО, и для целевой записи это неверно.**
Скорость измерена сопоставлением продольных профилей по дискретным ориентирам
(`python -m tools.measure_speed`):

| Запись | Медиана, км/ч | Разброс p25…p75 | Вырожденных кадров |
|---|---:|---:|---:|
| `doubleT_obstacle` | **0.0** | −0.1…0.1 | 0 % |
| `doubleT_platform` | 18.8 | 2.0…42.0 | 0 % |
| `roundT_doubleT` | 61.2 | 56.8…64.7 | 12 % |
| `roundT_pressureGate_roundT` | 53.9 | 50.5…57.5 | 9 % |
| `roundT_squareT_pressureGate_squareT` | 46.9 | 38.3…50.4 | 29 % |
| `squareT_platform_squareT_switch` | 5.1 | 0.0…29.5 | 4 % |

**В `doubleT_obstacle` состав стоит.** За все 20.39 с записи продольное смещение
равно 0.00 м, причём пик корреляции резкий (8–9.5 σ), то есть это измерение, а не
отсутствие измерения. Сцена статическая: препятствие находится на одной и той же
дистанции во всех 201 кадрах.

Остальные пять записей сняты в движении. Широкие разбросы у `doubleT_platform`
(2→42 км/ч) и `squareT_platform_squareT_switch` (0→29 км/ч) — это торможение
перед станцией и манёвры у стрелки, а не шум оценки.

Доля вырожденных кадров растёт на гладких круглых участках и падает там, где
много ориентиров, — как и должно быть при апертурной вырожденности.

**4.6. Пять «чистых» записей — ПРОВЕРЕНО частично, пустыми считать нельзя.**
Гипотеза §4.2 о том, что остальные пять записей дают «нормальную» обстановку,
проверена сканом габарита (коридор вокруг покадровой оси, кластеры выше головки
рельса). Препятствий, похожих на фигуру, на трёх `roundT`-записях не найдено.

Но найдено другое:

- `squareT_platform_squareT_switch`, кадры 735–772 — вертикальная конструкция
  высотой ~2.8 м у самой кромки габарита, прослеживается с 65 м до 48 м.
  Судя по участку — мачта или привод стрелки. Постоянный источник ложных тревог;
- **ретрорефлекторы внутри габарита**: 126 кадров из 293 на записи со стрелкой,
  35 из 115 на записи с платформой, медианная дальность 12–15 м. Это путевая
  инфраструктура, а не жилеты.

Следствие: оракул `tools/oracle.py` на этих записях вернёт разметку из отражателей,
то есть ложные положительные примеры в ground truth. Расширять его на «чистые»
записи нельзя. Положительные примеры на однопутном участке получаются только
синтетикой.

**4.7. Дальность прослеживания оси — свойство сенсора, а не алгоритма.**
Скользящий угол падения на полированную головку рельса уничтожает возврат:
в полосе головок при `|y| < 2.5` остаётся 83 точки на 25–30 м, 19 на 35–40 м
и 0 на 50–55 м. Перебор параметров трассера не помогает.

| что прослеживается | дальность |
|---|---:|
| ось по головкам рельсов, покадрово (2 пути) | 26 м |
| то же, накопление 20 кадров | 44 м |
| ось по полосе основания, покадрово (1 путь) | 55 м |
| центр свободного сечения тоннеля | 110–135 м |
| хоть какие-то возвраты | ~190 м |

Ориентир 300 м недостижим физически: за 190 м возвращается 2–4 точки на слой 10 м.

## 5. Задача

**Обнаружить препятствие на пути беспилотного поезда и определить расстояние до него.**

Что играет за нас:

- дальность измеряется **напрямую**, это не монокулярная оценка глубины — расстояние до любой
  точки есть `norm(x, y, z)` с точностью сенсора;
- обзор вперёд более 200 м;
- пять записей без препятствий работают как модель нормального фона.

Что играет против:

- нет разметки — ни одного размеченного препятствия, метрику качества придётся определять самим;
- нет одометрии и TF — положение рельсов и габарита приближения строений неизвестно, «опасная
  зона» не задана;
- неизвестна геометрия установки лидара (высота, наклон), поэтому «уровень пути» надо выводить
  из самих данных;
- тоннель — замкнутое пространство: стены, кабельные лотки, ниши и сам гермозатвор постоянно
  дают отражения внутри коридора, и отделить их от реального препятствия сложнее, чем
  на открытой местности;
- 62 % ячеек пустые, плотность сильно падает с расстоянием.

Главный вопрос не «как измерить расстояние» (это тривиально), а **«какие точки считать
препятствием»**: как отделить объект в габарите пути от стен, платформы, гермозатвора и
путевого оборудования.

## 6. Открытые вопросы для обсуждения

1. Как задать габарит приближения строений, не имея ни калибровки лидара, ни разметки пути?
   Выводить ось пути из геометрии тоннеля покадрово или оценить один раз и зафиксировать?
2. Стоит ли строить модель фона по пяти «чистым» записям и искать отклонения, или надёжнее
   чисто геометрический критерий внутри одного кадра?
3. Как обойтись без ground truth: размечать вручную несколько десятков кадров или

## 7. Среда

ROS 2 не установлен. Чтение идёт через Python-пакет `rosbags` (0.11.5) без ROS:

```python
from pathlib import Path
from rosbags.highlevel import AnyReader
from rosbags.typesys import Stores, get_typestore

ts = get_typestore(Stores.ROS2_HUMBLE)          # обязательно: в баге v5 нет определений типов
with AnyReader([Path("doubleT_obstacle")], default_typestore=ts) as r:
    for conn, stamp, raw in r.messages(connections=list(r.connections)):
        msg = r.deserialize(raw, conn.msgtype)
        ...
```

Без `default_typestore` падает с `AnyReaderError: Bag contains no type definitions`.

Визуализация: `open3d` 0.19 под WSL2 работает только программным рендером, GPU не проброшен
(`/dev/dri` отсутствует), и GLFW надо увести с Wayland на X11:

```bash
LIBGL_ALWAYS_SOFTWARE=1 GALLIUM_DRIVER=llvmpipe WAYLAND_DISPLAY=no-wayland DISPLAY=:0 ./view.py
```

Один кадр в памяти ≈ 11 МБ после фильтрации (float32, xyz), вся запись целиком не помещается —
загружать по частям.

**Страничный кэш под WSL2.** Процесс прогона занимает ~240 МБ, но ядро Linux держит
прочитанные файлы записей в кэше: +5.8 ГиБ после одной записи 6.6 ГиБ. Кэш держит
виртуальная машина WSL; при `memory=30GB` в `.wslconfig` и 31.5 ГБ у хоста шесть
записей подряд доводили её до лимита, и Windows её роняла. Читатель записей
(`tools/bag_reader.py`) теперь сам отдаёт прочитанные страницы
(`bag.release_page_cache_every_frames`). Потоки BLAS разумно ограничивать:
`OMP_NUM_THREADS=8 OPENBLAS_NUM_THREADS=8` — время обработки тогда другое,
и каждая таблица времени указывает число потоков.

**Запись rosbag2 из `rosbags`.** Писатель `rosbags` 0.11.5 умеет только формат
версий 8 и 9, а исходные записи — версии 5 (Humble). Копия записи с изменёнными
облаками (`tools/make_scenario_bag.py`) поэтому делается копированием файла
и заменой поля `data` в базе sqlite: формат, метаданные и штампы остаются
побайтно исходными.
