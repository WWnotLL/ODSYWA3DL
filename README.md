## Геометрия вместо нейросетей, или как работает наш алгоритм 

### 💡 Философия подхода
Вместо того чтобы обучать нейросеть распознавать человека, ящик или кошку, мы пошли другим путём: мы научили систему распознавать **«идеальный пустой тоннель»**. 
Алгоритм строит математическую модель пути и нормативного габарита. Всё, что вписывается в эту модель — игнорируется. Всё, что выходит за её рамки — считается препятствием. Это делает систему невероятно устойчивой к новым участкам тоннеля.

Такое решение было принято в связи с тем, что из-за отсутствия размеченных данных обучить модель распознавать очень сложно и, скорее, даже невозможно.

---

### ⚙️ Пошаговый конвейер обработки

Обработка одного кадра лидара проходит в 4 этапа:

#### Шаг 1. Ориентация в пространстве
Все окружающие предметы наш поезд может видеть только благодаря лидару, соответственно, его местоположение будет являться началом системы координат. Однако лидар вращается и движется вместе с поездом, поэтому нам нужно "зацепиться" за что-то постоянное, чтобы в дальнейшем понять, где находится препятствие. В случае с поездом наилучший вариант - "зацепиться" за землю.
* **Как это работает:** Алгоритм использует метод RANSAC - математическое "отсеивание" точек огромного количества ненужных точек, чтобы найти плоскость пола и выделить точки, принадлежащие рельсам.
* **Результат:** Система строит динамическую систему координат, привязанную к пути (X — направлена вперед вдоль рельсов, Z — направлена вертикально вверх, а Y дополняет систему до правой, соответственно, направлена влево перпендикулярно оси X) и вычисляет точное положение поезда в тоннеле.

#### Шаг 2. Построение "запретной зоны"
На основе найденной оси пути система строит 3D-коридор — **нормативный габарит приближения строений (Контур Ом, ГОСТ 23961-2024)**. 
* **Правило простое:** внутри этого коридора, над уровнем пола, не должно быть ничего, кроме самого поезда.

#### Шаг 3. Поиск "нарушителей" и кластеризация
* Система берет сырое облако точек и отфильтровывает всё, что находится вне "запретной зоны": стены тоннеля, кабели, потолок;
* Точки, попавшие внутрь "запретной зоны", группируются в кластеры (потенциальные объекты);
* Для каждого кластера вычисляется центр, рамка объекта и расстояние до поезда.

#### Шаг 4. Проверка временем 
Одиночный кадр может содержать шум, блики или пыль, которые алгоритм может принять за объект. Чтобы избежать ложных торможений, мы используем **временной фильтр**: объект считается реальным препятствием только если он был уверенно зафиксирован как минимум в **3 из 5 последних кадров**.
* Это полностью отсекает случайные шумы и делает систему надежной.

---

### 🚦 Логика принятия решений

Система выдает команду на остановку в двух случаях:

1. **Прямая угроза (`obstacle_found = True`):** 
   Временной фильтр подтвердил наличие кластера точек внутри "запретной зоны". Система выдает расстояние до ближайшей точки препятствия.
2. **Потеря ориентации (`verdict.stop = True`):** 
   Если система внезапно потеряла из виду рельсы (например, из-за сильного загрязнения датчика или резкого поворота), но до этого в коридоре был замечен подозрительный объект — срабатывает принцип **«Безопасность прежде всего»**, и поезд останавливается.

### 🧮 Математическая модель в двух словах

В основе лежит чистая евклидова геометрия и статистика. 
1. **Система координат пути:** Вычисляется через минимизацию расстояния от точек пола до плоскости - метод наименьших квадратов в RANSAC.
2. **Уверенность обнаружения:** Рассчитывается как отношение запаса расстояния от кластера точек до начала "запретной зоны" к неопределенности положения оси пути. Чем ближе объект к центру поперечного сечения "запретной зоны" — тем выше уверенность.
3. **Отсутствие ML:** В ядре алгоритма нет весов нейросетей, градиентного спуска или обучения. Это детерминированная математическая функция: `f(облако_точек) -> решение`.

### Docker
Образ собирается из docker/Dockerfile, сервисы описаны в docker-compose.yml: demo нода и RViz, detector только нода, rviz только RViz, ros2 консоль. Папки ROS2 folder/src и data подключены в контейнер, поэтому правки кода и конфига работают без пересборки. Новые файлы и пакеты требуют docker compose build.

Перед запуском любого сервиса сам запускается служебный network-setup. Он поднимает на компьютере предел буфера сокета (net.core.rmem_max) до 64 МБ, иначе облака по 8 МБ частично теряются по пути к ноде. Общий буфер для остальных программ не меняется. Настройки DDS лежат в docker/cyclonedds.xml.

Окна (RViz) открываются через файл авторизации текущего сеанса, xhost не нужен. Если RViz всё же пишет, что не может подключиться к дисплею, выполните на компьютере xhost +local:docker.

ROS_DOMAIN_ID берётся из терминала, по умолчанию 0. Если на компьютере работает другой ROS и мешает, запускайте так: ROS_DOMAIN_ID=42 docker compose up demo, и в остальных терминалах с тем же номером.

### Алгоритм запуска
#### 1. Клонируйте репозиторий
   ```
   git clone https://github.com/WWnotLL/Obstacle-detection-system-with-a-3D-lidar.git
   cd Obstacle-detection-system-with-a-3D-lidar
   ```

**Все команды выполняются из корня репозитория**


#### 2. Один раз соберите Docker-образ
   ```
   docker compose build
   ```
#### 3. Запуск четырех терминалов
Терминалы 2–4 можно запускать двумя способами, оба работают одинаково: отдельными контейнерами (docker compose run, как ниже) или внутри контейнера demo (docker compose exec, [в конце раздела](#запуск-терминалов-в-работающем-контейнере)).<br>
**Терминал 1 - нода и RViz.** <br>
Если nvidia-container-toolkit нет (RViz рисует на процессоре):
   ```
   docker compose up demo
   ```
Если есть видеокарта NVIDIA и nvidia-container-toolkit (RViz рисует на видеокарте, плавнее):
   ```
   docker compose -f docker-compose.yml -f docker-compose.gpu.yml up demo
   ```
**Терминал 2 - полный результат по каждому кадру:**
   ```
   docker compose run --rm ros2 ros2 topic echo /obstacle/state obstacle_detector_msgs/msg/ObstacleState
   ```
**Терминал 3 - только сигналы "тормозить" или "продолжать движение" (true или false):**
   ```
   docker compose run --rm ros2 ros2 topic echo /obstacle/state obstacle_detector_msgs/msg/ObstacleState --field stop
   ```
**Терминал 4 - проигрывание записи с препятствием (запускать, когда RViz уже открылся):**
   ```
   docker compose run --rm ros2 ros2 bag play /workspace/data/scenarios/roundT_doubleT_approach_figure
   ```

Записи лежат в /workspace/data/for_hackathon/: doubleT_platform, roundT_doubleT, roundT_pressureGate_roundT, roundT_squareT_pressureGate_squareT, squareT_platform_squareT_switch.

Запись играется один раз, для повтора запустите команду ещё раз. Чтобы крутилась по кругу, допишите в конце --loop и на каждом новом круге нажимайте Reset в RViz внизу слева.

Если не хватает вычислительных мощностей, можно проигрывать запись медленнее, дописав --rate 0.5.

#### Запуск терминалов в работающем контейнере
Терминалы 2, 3, 4 можно запускать и в уже работающем контейнере demo, без новых контейнеров: вместо docker compose run --rm ros2 пишите docker compose exec demo:
   ```
   docker compose exec demo ros2 topic echo /obstacle/state obstacle_detector_msgs/msg/ObstacleState
   docker compose exec demo ros2 topic echo /obstacle/state obstacle_detector_msgs/msg/ObstacleState --field stop
   docker compose exec demo ros2 bag play /workspace/data/scenarios/roundT_doubleT_approach_figure
   ```

**Что смотреть**
В /obstacle/state на каждый кадр приходит:

- header.stamp время кадра
- state 0 путь свободен, 1 не проверен, 2 препятствие
- stop нужно ли тормозить
- obstacle_found найдено ли препятствие
- nearest_distance_m расстояние до препятствия вдоль пути в метрах (nan, если его нет)
- checked_range_m на сколько метров вперёд путь проверен
- obstacles список препятствий: расстояние, центр, размер, число точек, уверенность
<br>
Чтобы смотреть одно поле, допишите к команде терминала 2 --field и имя поля, например --field nearest_distance_m.
<br>
В RViz видно облако лидара, синюю линию оси пути, зелёные границы проверенного участка и красный куб на месте препятствия. Если после смены записи разметка пропала, нажмите Reset внизу слева.

**Запись результатов**
Пока играет запись, в отдельном терминале:


## Описание ROS2
#### Подписки и публикации
Нода слушает сразу два топика, /lidar_points и /sensing/lidar/hesai128/pointcloud (sensor_msgs/PointCloud2). Другой топик можно добавить в конфиг или указать при запуске. В облаке нужны поля x, y, z, intensity, желательно ещё ring и timestamp.

Публикует:

- /obstacle/state - главный результат, тип obstacle_detector_msgs/ObstacleState. Одно сообщение на каждый кадр лидара, время в нём то же, что у кадра. Поля описаны выше в разделе Что смотреть.
- /obstacle/markers - разметка для RViz (visualization_msgs/MarkerArray) в системе пути track: синяя линия оси пути, две зелёные линии границ проверенного участка и красный куб на каждое найденное препятствие. Каждый кадр старая разметка стирается и рисуется заново.
- /obstacle/cloud_preview - копия облака лидара для RViz (sensor_msgs/PointCloud2) только с полями x, y, z, intensity и без пустых точек. Сколько точек в ней оставлять, задаёт preview_point_step.
- /tf - положение системы пути track относительно лидара. Её каждый кадр находит алгоритм: ось X идёт вдоль пути вперёд, Z вверх. Публикуется, только когда путь найден.
- /tf_static - положение лидара на поезде, base_link → hesai_lidar. Публикует launch-файл по аргументам lidar_x, lidar_y, lidar_z, поворот берётся из конфига алгоритма.

#### TF
TF в ROS хранит, как системы координат расположены друг относительно друга. У нас их три, цепочкой:

base_link → hesai_lidar → track

- base_link - поезд. От него считается всё остальное, в RViz это Fixed Frame.
- hesai_lidar - лидар, в его координатах приходит облако. Где он стоит на поезде, задают lidar_x, lidar_y, lidar_z при запуске. Это положение не меняется, поэтому идёт в /tf_static.
- track - путь впереди. Его каждый кадр заново находит алгоритм, поэтому он идёт в /tf. В этой системе рисуется разметка и считаются расстояния до препятствий.
Благодаря этой цепочке RViz сам ставит облако и разметку на свои места. Если стоит другой лидар, достаточно поменять lidar_frame и положение при запуске.

#### Конфигурация
Все настройки в одном файле ROS2 folder/src/obstacle_detector/config/obstacle_detector.yaml. Сверху параметры ноды, под ключом core конфиг алгоритма. После правки перезапустите терминал 1.

**Параметры ноды:**

- pointcloud_topics - список топиков, откуда брать облако, по умолчанию /lidar_points и /sensing/lidar/hesai128/pointcloud
- track_frame - имя системы пути в TF и разметке, по умолчанию track
- lidar_period_s период кадров лидара в секундах, 0.1 для 10 Гц. По нему нода понимает, сколько кадров пропущено между двумя пришедшими, и сообщает это алгоритму.
- record_jump_s если между кадрами прошло больше этого времени (или время пошло назад), нода считает, что началась другая запись, и сбрасывает алгоритм. По умолчанию 1 с.
- required_range_m на сколько метров вперёд путь должен быть проверен, чтобы считаться свободным (state 0). Если проверено меньше, будет state 1. По умолчанию 0, то есть хватает любой проверенной дальности.
- preview_point_step сколько точек отдавать в RViz: 1 все, 2 каждую вторую и так далее. Если RViz тормозит, поставьте 2 или 4. На работу алгоритма не влияет.
- core настройки самого алгоритма, перенесены из его конфига без изменений.
Положение лидара на поезде задаётся при запуске аргументами lidar_x, lidar_y, lidar_z, по умолчанию 0, 0 и 1.081 м.<br>

#### Launch-файлы
Лежат в ROS2 folder/src/bringup/launch/:

- detector.launch.py нода и положение лидара на поезде
- rviz.launch.py RViz с конфигом bringup/config/lidar_monitor.rviz
- demo.launch.py оба сразу

Через Docker их запускают сервисы demo, detector и rviz:
   ```
   docker compose up demo
   docker compose up detector
   docker compose up rviz
   ```
demo запускает по факту под собой и детектор и рвиз одновременно

Или вручную из консоли ROS (docker compose run --rm ros2):
   ```
   ros2 launch bringup demo.launch.py
   ```
Аргументы пишутся через :=, например ros2 launch bringup demo.launch.py lidar_z:=1.5

- pointcloud_topic слушать только этот топик вместо списка из конфига, например pointcloud_topic:=/my_lidar/points
- lidar_frame frame_id облака, по умолчанию hesai_lidar
- lidar_x, lidar_y, lidar_z положение лидара на поезде в метрах
- bag путь к записи, чтобы она проигралась вместе с нодой
- detector_params свой конфиг вместо obstacle_detector.yaml

### 🎯 Дальность обнаружения

#### Рабочая зона

| Зона | Дальность | Комментарий |
|---|---|---|
| **Слепая зона** | < 5 м | Из-за угла наклона лидара и неравномерности лучей по углу места |

#### Влияние размера объекта на дальность

Инъекция тела на ось пути в запись `roundT_doubleT` (61 км/ч, 241 кадр, 25 заходов):

| Объект (ширина × высота) | 10 м | 20 м | 30 м |
|---|---|---|---|
| 0.20 × 0.20 м (порог) | 50% | нестабильно | нестабильно |
| 0.24 × 0.25 м | 77% | 77% | 77% |
| 0.30 × 0.30 м | 84% | 84% | 84% |
| 0.20 × 0.40 м | 100% | 100% | 100% |
| 0.50 × 1.70 м (человек) | 100% | 100% | 100% |

**Ключевой инвариант:** минимальная обнаружимая площадь над полом габарита **A_min ≈ 0.025–0.042 м²**. Предмет на пути обязан подниматься над уровнем головки рельса хотя бы на 0.25–0.30 м при ширине 0.3 м — это масштаб рюкзака или небольшого ящика.

#### Ближняя зона 5–10 м — хуже средней

Предмет 0.24 × 0.25 м (0.042 м² над полом) обнаруживается в **28% кадров** на 5–10 м против **95% кадров** на 10–24 м. Причина — физическая: плотность лучей по углу места неравномерна, ниже −6° лучи разрежаются. Это свойство сенсора, а не алгоритма.

#### Природа ложных срабатываний

Все ложные тревоги — это **стационарные конструкции, стоящие в 0–30 мм снаружи кромки габарита Ом**:

1. **Конструкция у правой кромки за концом рельсовой базы** (`roundT_squareT`): лицо в +16…+30 мм от кромки, эпизод на кадрах 32–37.
2. **Грань в верхнем боковом углу габарита** на стрелочной записи: −2…+25 мм, кадры 232–296 и 723–728.
3. **Край платформы** на станционных записях — нормативное исключение п. 2.1.2 ГОСТ 23961-2024, закрыто условным вырезом платформы.

**Механизм:** тревогу решают сантиметры ошибки оси и шума лица. При невязке оси 10–14 см и проникновении объекта на 2–10 см — объект оказывается внутри «запретной зоны» из-за погрешности, а не из-за реального нарушения габарита.

### ⚠️ Сложные случаи и ограничения

#### Что алгоритм обнаруживает надёжно
- Человек в габарите пути на дистанции до 26 м — 100% кадров
- Ящик 0.3×0.3 м на 10–24 м — 84% кадров
- Строительное оборудование, упавшие предметы выше 0.25 м — при площади > 0.04 м² над полом

#### Что алгоритм не обнаруживает
- Предметы ниже 0.15 м над уровнем головки рельса (пол габарита)
- Объекты в слепой зоне < 5 м (физическое ограничение сенсора)
- Прозрачные/поглощающие поверхности (стекло, чёрный пластик)
- Движущиеся объекты со скоростью, совпадающей со скоростью поезда

#### Граничные случаи
- **Стрелочный перевод:** 60% кадров вне норматива (прямая ось не определена). Объявлен непокрытой зоной.
- **Станционная платформа:** край платформы — нормативное исключение, закрыто условным вырезом.
- **Кривые участки:** прямая ось отклоняется от дуги, база укорачивается по нормативному зазору 113 мм.

### 📝 Выводы из экспериментов

1. **Геометрия + нормативный габарит** даёт лучшее соотношение качество/скорость/обобщаемость, чем нейросети на наших данных.
2. **Временной анализ критически важен** — без него 14 эпизодов вместо 4.
3. **Дальность задаёт физика сенсора**, а не алгоритм: скользящий угол на головках рельсов ограничивает базу 26 м.
4. **Ложные тревоги решаются сантиметрами** — конструкции в 0–30 мм от кромки габарита требуют либо улучшения точности оси, либо порога уверенности на уровне потребителя.

## Эволюция подхода

*Полный технический разбор доступен в [EVOLUTION.md](https://github.com/WWnotLL/Obstacle-detection-system-with-a-3D-lidar/blob/main/docs/EVOLUTION.md). Ниже — ключевые вехи.*

Мы пришли к финальному решению не сразу. Ниже показан ход наших мыслей при обсуждении планов по решению задачи, ниже представляем вам ккак мы отсеивали гипотезы:
|№|Название гипотезы|Комментарий|
|---|---|---|
|1. | **Нейросети** | *Отвергнута.* Нет размеченных данных. Обнаружили «ловушку интенсивности»: люди в жилетах имеют отклик 255 (при медиане 11). Детектор выучил бы «жилет», а не «препятствие».|
|2. | **Чистая геометрия (Прямоугольный габарит)**|  *Провал.* 94-100% ложных срабатываний. Стены и кабели попадали внутрь прямоугольника.|
|3. | **Нормативный габарит «Ом» (ГОСТ 23961-2024)**| ✅ *Прорыв.* Ложные тревоги упали с 94% до **2.3%**. Но на кривых участках прямая ось пути давала новые ошибки.|
|4. |**Ось пути Б′ (Рельсы + Полоса основания)**| ✅ *Решение.* Рельсы задают точную ось (короткая база), полоса пола продлевает её. Ложные тревоги на круглых участках упали до **0.0%**.|
|5. |**Временное подтверждение «3 из 5»**| ✅ *Финализация.* Сняло 71% коротких эпизодов (шум, пыль). Итоговая частота ложных тревог: **1.3 эпизода в минуту**.|
|6. |**Условный вырез платформы**| ✅ *Уточнение.* Безусловный вырез создавал слепую полосу 123 мм на всю запись. Включили вырез только на подтверждённой платформе — обнаружение выросло с 0% до **92%**.|
|7. |**Опускание пола габарита**| ✅ *Уточнение.* Пол был поднят на 0.38 м, из-за чего предметы высотой 0.25 м имели действующую площадь только 40%. Опустили до 0.305 м + маска рельсов — площадь выросла до **0.042 м²**, предмет перешёл из «границы |обнаружимости» в надёжную зону.

**Почему этот подход работает:**
1. **Не требует размеченных данных** — критично для нашей задачи.
2. **Использует специфику среды** — тоннель статичен, габарит нормативен.
3. **Быстрый** — real-time на CPU (12-25 FPS).
4. **Интерпретируемый** — понятно, почему сработал.
5. **Обобщается** — геометрия одинакова на любом участке метро.
