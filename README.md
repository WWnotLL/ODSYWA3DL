# Ядро обнаружения препятствий по лидару (v0.2)

Ядро получает один кадр облака точек переднего лидара поезда метро. Оно находит пол, ось пути и нормативный габарит приближения строений (контур Ом, ГОСТ 23961-2024). Всё, что попало внутрь габарита выше пола, собирается в кластеры. Тревога — только если кластер заходит в габарит поезда 2.1 × 3.0 м (размер — данные организаторов; высота отсчитана от основания пути по нашей сверке с их синтетической записью; вокруг оси пути): 4-я по глубине точка кластера — внутри. Затем тревога подтверждается во времени («3 кадра из 5»). На выходе — есть ли препятствие и расстояние до ближайшего. Других датчиков ядру не нужно: ни одометрии, ни TF, ни камер. Машинного обучения нет, только геометрия. Ядро — чистая библиотека на numpy без ROS; нода вызывает её на каждый кадр.

## Установка

Python 3.12 (3.10).

```bash
pip install -r requirements-core.txt    # только ядро: numpy, PyYAML, scipy
pip install -r requirements-tools.txt   # + чтение записей, тесты, визуализация
```

Для ноды достаточно `requirements-core.txt`. В ядре нет импортов ROS, sklearn, open3d, rosbags и matplotlib — это проверяется тестом.

Потоки BLAS задавайте явно — от них зависит время кадра:

```bash
export OMP_NUM_THREADS=8 OPENBLAS_NUM_THREADS=8
```

## API

```python
from core.config import Config
from core.pipeline import ObstacleDetector

detector = ObstacleDetector(Config.from_yaml("configs/default.yaml"))
result = detector.process(xyz, intensity, ring, t_rel, stamp_ns, frame_gap=1)
```

Все параметры лежат в `configs/default.yaml`. Если ключа не хватает или есть лишний, загрузка завершается ошибкой.

**Вход `process()`** — сырой кадр `PointCloud2` без каких-либо преобразований, со всеми точками, включая пустые лучи (0, 0, 0):

| аргумент | что | форма, тип |
|---|---|---|
| `xyz` | поля `x`, `y`, `z` | (N, 3), float32 |
| `intensity` | поле `intensity` | (N,), float32 |
| `ring` | поле `ring` | (N,), uint16 или `None` |
| `t_rel` | поле `timestamp` точек (часы сенсора; используются только разности) | (N,), float64 или `None` |
| `stamp_ns` | `header.stamp` в наносекундах | int |
| `frame_gap` | сколько кадров записи прошло с прошлого вызова (1 — ни одного не пропущено) | int |

Если в облаке нет полей `ring` и `timestamp`, передавайте `None, None` явно: пары двойного эха ядро найдёт по направлению луча (на шести записях — тот же результат, что с полями), но кадр считается примерно вдвое дольше (см. «Время кадра»). Только одно из двух `None` — кадр `checked = False`.

Раскладка точки упакованная, без выравнивания: `timestamp` лежит по смещению 18. Поэтому dtype строится по `fields` сообщения с явными `offsets` и `itemsize = point_step`. Готовая функция — `cloud_to_arrays()` в `examples/run_frames.py`; `msg.data` из rclpy подходит для `np.frombuffer` так же.

**`reset()`** вызывайте при старте ноды и при скачке записи (перемотка, новая запись). Пропуски кадров сообщаются через `frame_gap`, а не через `reset()`; между соседними кадрами он не нужен. После него снова идёт холодный старт (см. ограничения).

Кадры подаются строго по одному и по порядку. Если нода пропускает кадры, передайте их число в `frame_gap`.

## Выход

`FrameResult` (контракт заморожен):

| поле | смысл |
|---|---|
| `obstacle_found` | есть подтверждённое препятствие в габарите |
| `nearest_distance_m` | дистанция до ближайшего подтверждённого препятствия или `None` |
| `detections` | список `Detection` — только подтверждённые |
| `debug` | диагностика, см. ниже |

`Detection`:

| поле | смысл |
|---|---|
| `distance_m` | продольная координата x ближайшей точки кластера |
| `centroid_xyz`, `bbox_min_xyz`, `bbox_max_xyz` | центр и рамка кластера |
| `n_points` | точек в кластере |
| `score` | уверенность 0…1: запас до кромки габарита против неопределённости оси |
| `source` | `gauge` |

**Система координат выхода — система пути, не лидара:** X вдоль пути вперёд, Y влево, Z вверх; z = 0 на плоскости путевого основания; начало — проекция сенсора на эту плоскость. **`distance_m` — вдоль пути** (продольная x), не дальность по лучу и не от лобовой части состава.

### Что из `debug` нужно ноде

| ключ | смысл |
|---|---|
| `checked` | **читать первым.** `False` — кадр непригоден (пустой, без возвратов, плоскость основания отвергнута, только одно из `ring` / `t_rel`); причина — в `detail` (только в лог, не ветвиться по тексту); тогда нет ключей `axis`, `corridor`, `frame_transform`. `obstacle_found = False` без `checked = True` — это «не проверено», а не «путь свободен» |
| `frame_gap` | сколько кадров прошло с прошлого проверенного, с учётом непригодных |
| `axis.state` | `measured` / `held` (ось удерживается по прошлым кадрам) / `degraded` / `lost`. **При потере оси это словарь со `state == "lost"`, не `None`** |
| `axis.reason` | почему ось не измерена: `anchor_uninitialised`, `tracer_failed` (рельсы не найдены), `gate_rejected`, `outlier_rejected`; у измеренной — `None`. Холодный старт бывает с обеими первыми причинами (на шести записях 45 кадров `anchor_uninitialised` и 9 `tracer_failed`), поэтому по `reason` не ветвиться — только в лог |
| `corridor.x_m` | `[ближняя, дальняя]` граница проверенного участка, м. Дальше дальней границы «пусто» не значит «свободно» |
| `frame_transform` | преобразование лидар → путь: `p_track = R @ p_lidar + t`, ключи `rotation` (3×3) и `translation_m` |
| `verdict` | правило остановки при потере оси: `stop` (bool), `reason`. Взведённый стоп держится и через непроверенные кадры: там `verdict` = `{"stop": true, "reason": "latched_through_unchecked"}`. Нет `verdict` в непроверенном кадре — это не отмена стопа |

**TF.** Плоскость пола оценивается заново в каждом кадре, поэтому преобразование динамическое. Публикуйте на каждый проверенный кадр TF от `frame_id` облака к системе пути (например, `track`) со штампом кадра: трансляция `t`, кватернион из `R`. Рамки и ось рисуйте в `track`. С `frame_id` облака они окажутся повёрнутыми на 90° и поднятыми на высоту сенсора.

### Три состояния пути

«Нет препятствия» и «путь свободен» — не одно и то же. По каждому кадру нода получает одно из трёх состояний:

| состояние | условие | что значит |
|---|---|---|
| **препятствие** | `obstacle_found` или `debug.get("verdict", {}).get("stop")` (в том числе в непроверенном кадре) | в габарите подтверждён объект, или ось пропала сразу после того, как в коридоре был кластер |
| **не проверено** | `debug["checked"] == False`, или `debug["axis"]["state"]` не `measured` и не `held` (то есть `degraded` или `lost`), или `debug["corridor"]["x_m"][1]` меньше требуемой дальности | ось не подтверждена или коридор короче нужного — о пути впереди ядро ничего не утверждает |
| **свободно** | всё остальное | ось `measured` или `held`, коридор проверен на `[x_m[0], x_m[1]]`, препятствий в нём нет |

- При `degraded` коридор в `debug` есть, но ось не проходит допуск — ядро само считает её потерянной (правило остановки В₂ работает так же). Это «не проверено», не «свободно». На шести записях таких кадров после старта 3 (стрелочная 759, 760, 772); 759–760 закрыты стопом В₂.
- При `lost` коридора нет.
- На шести записях все 54 кадра `lost` — это холодный старт после запуска: 9, 11 и 34 кадра на трёх записях. Потеря оси на ходу и `hold_expired` не встречались ни разу.
- Требуемую дальность и действие при «не проверено» (снизить скорость, остановиться, не трогаться) задаёт нода или команда. Ядро это решение не принимает.
- Проверенный участок сейчас кончается на 21–26 м: это медиана по записям, подробнее в разделе ограничений.

**Ложные тревоги на пяти записях без препятствий** (2287 кадров, 3.8 мин) — **0**. Кандидаты (кластеры до порога глубины и подтверждения) остаются в `debug["candidates_raw"]`:

|---|---:|---:|---:|---:|
| `doubleT_platform` | 38 | 0 | 0 | 0 |
| `roundT_doubleT` | 0 | 0 | 0 | 0 |
| `roundT_pressureGate_roundT` | 8 | 0 | 0 | 0 |
| `roundT_squareT_pressureGate_squareT` | 12 | 0 | 0 | 0 |
| `squareT_platform_squareT_switch` | 503 | 0 | 0 | 1 (кадры 759–760, 0.5 м) |

В v0.1 было 27 кадров с тревогой, 5 эпизодов (1.3 в минуту, 18.1 м пути). Эпизод — одна команда на торможение: тревоги с паузой не больше 1 с.

```bash

python -m tools.false_alarm_table --config configs/default.yaml --runs runs/v02_default --summary
```

**Запас до ложной тревоги мал в одном месте.** Самый глубокий ложный кандидат — 17 мм снаружи габарита поезда: стрелочная, кадр 760, 51 м, ось целиком по полосе основания в состоянии `degraded`. На рельсовой части запас 366 мм, на продлении за стыком — 134 мм. Стоп на 759–760 — правило В₂ (ось пропала сразу после кандидата), кадр 772 — «не проверено».

**Цена габарита поезда.** Объекты у кромки габарита Ом, но внутри габарита поезда, находятся позже, чем с одним габаритом Ом: на синтетике организаторов 25.7 → 20.1 м и 20.6 → 12.6 м.

**Холодный старт.** После запуска и после `reset()` коридора нет, пока ось не захвачена: 0 / 9 / 11 / 0 / 0 / 34 кадра по шести записям (до 3.4 с), всего 54 кадра и 69.4 м пути. По правилу организаторов «не проверено» без сбоя лидара засчитывается как ошибка. Тело в сцене задерживает захват: фигура на оси — на 3 кадра, брусок у кромки — на 16 (`tools/scenarios.py --trace-anchor`).

```bash
python -m tools.axis_coverage --runs runs/confirm_fix
```

**Рабочая зона.**
- От 5 м до конца рельсовой базы: медиана 21.3–26.3 м по записям. Ближе 5 м — слепая зона.
- В 8.0 % кадров (198 из 2488) база продлена по полосе основания: коридор до 31 м по медиане, p90 41 м, максимум 51 м. На продлённом участке ось смещена вправо на 62–115 мм. Это измерено только на 25–39 м; дальше 39 м смещение не мерилось (`tools/measure_extension_residual.py`).

**Ближняя зона 5–10 м хуже средней.** Предмет 0.24 × 0.25 м находится в 53 кадрах из 71 (75 %; в v0.1 — 20, 28 %) на 5–10 м против 161 из 170 (95 %) на 10–22 м (слой A, без подтверждения). Причина — лучи по углу места неравномерны.

```bash

    --advance-m 1.7 --distance-m 22 --first-frame 10 --last-frame 251 --via-pipeline --no-confirm \
    --body-radius 0.12 --body-height 0.25 --out out/v02_near
```

**Минимальный объект и кабель.** Тело 0.3 × 0.3 × 0.1 м на головке рельса находится в 37–42 % кадров на 10–40 м, первая детекция около 16 м. Кабель 0.05 × 1.0 м (вертикальный и под 45°) не находится: на 10–40 м — 0 кадров из 172 при пороге числа точек v0.2 (мерено с маской по головкам; с настройками по умолчанию отдельно не мерено), только на 5–8 м и только при пороге 21 точка на 10 м (v0.2 — 30, v0.1 — 60). На нём слишком мало точек: 10 на 10–15 м.

**Дальность.** Проверенный участок кончается на 21–26 м (конец рельсовой базы оси). Первая детекция в сценариях сближения — около 18 м: она ограничена стартом сценария (20–26 м) и концом проверенного участка. Дальше 21–26 м ядро v0.2 путь не проверяет. Критерий организаторов — первая верная детекция: больше 100 м «хорошо», меньше — «плохо»; v0.2 — «плохо». Дальняя зона — в следующей версии.

- Габарит поезда, пол и порог числа точек v0.2 время не меняют (в одном сеансе `detect` 4.7–4.8 мс на 307k — как без них).

## Проверка ноды

Ядро детерминировано. Одна и та же запись через ноду должна дать ровно те же числа. Если нода даёт другие, ошибка в обвязке, а не в ядре. Выход не зависит от того, какой штамп подаётся: `header.stamp` или время записи rosbag2. Проверено: 0 расхождений на 345 кадрах.

**1. Позитив — копия `roundT_doubleT` со вписанной фигурой 0.5 × 1.7 м** (`roundT_doubleT_approach_figure` и `figure_truth.json`, передаются отдельно). Вся запись, 252 кадра:

| что считать | ожидается |
|---|---:|
| кадров с непустым `candidates_raw["detections"]` | 226 |
| из них с кандидатом на фигуре | 224 |
| кадров с `obstacle_found` | **174** |
| из них тревога на фигуре | **174** (мимо — 0) |
| кадров с `axis.state == "lost"` | 14 |
| кадров с кандидатом мимо фигуры (кандидатов в них — 8) | 7 |

```bash

    --bag <путь>/roundT_doubleT_approach_figure --first 0 --last 251
```
